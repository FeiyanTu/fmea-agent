# 「功能分析过程需关注零件之间的关系」——需求符合性排查报告

排查时间：2026-09-30
排查对象：`D:\agent-fmea\fmea-agent`

---

## 一、结论

**部分符合，但生产环境实际不满足。**

- **数据模型层**：✅ 支持（`FunctionRelation` 已定义 5 种关系类型，含同级"功能配合"）
- **代码实现层**：⚠️ 只有"单 Agent 降级路径"实现了真正的功能网构建；**这条路径在生产中不走**
- **生产实际链路（多 Agent 路径）**：❌ 产出的"关系"只是结构树父子边，没有零件间（同级/接口/装配）关系
- **下游消费层**：❌ 功能表、功能网弹窗、失效分析都拿不到零件间关系

一言以蔽之：**用户提出的感受是对的——当前功能分析阶段确实没有真正关注零件之间的关系。** 底层具备能力，但生产链路把它绕过去了。

## 二、分层证据

### 2.1 模型层：具备（但仅限"功能关系"，结构层无接口关系）

| 位置 | 内容 | 评价 |
|---|---|---|
| `models/function.py:94-111` | `FunctionRelation`：`relation_type` 取值 `需要-满足` / `功能配合` / `冗余备份` / `接口关联` / `安全功能` | ✅ 「功能配合」即同级零件耦合，「接口关联」即接口关系 |
| `models/function.py:41` | `FunctionDetail.flow_type`：电气/机械力/热/流体/信号 | ✅ 可表达零件间能量流/信号流传递 |
| `models/function.py:31` | `child_node_id` — 每条功能绑定一个下一级节点 | ⚠️ 只表达纵向（父子），不含横向 |

### 2.2 生成层：分两条路，只有降级路径实现了

**路径 A — 单 Agent（`agents/step2_function.py`，有完整实现）**

`build_function_network_v4()`（`step2_function.py:403-508`）三阶段：

1. `_keyword_matching()`（`:514`）— 关键词交集 ≥2 时预建父子"需要-满足"边
2. `_llm_batch_match()` / `_llm_match_single()`（`:571-714`）— LLM 语义判断父子需满足
3. **`_enhance_network_v4()`（`:720-857`）— 唯一产出零件间关系的地方**：让 LLM 推断同级"功能配合"、"冗余备份"、"接口关联"、"安全功能"

**路径 B — 多 Agent（`orchestrator/function_multi_agent_runner.py`，生产默认走这条）**

`main.py:514`：`use_multi_agent = os.getenv("FMEA_FUNCTION_USE_MULTI_AGENT", "1") == "1"` → **默认开启**，失败才降到路径 A（`main.py:572`）。

### 2.5 现状功能表达"关系"的唯一方式

功能表的三列表（①/②/③）与每条功能的 `upper_function` / `description` / `lower_function`，是当前表达"关系"的**唯一载体**，而且**只覆盖纵向父子分解**。同级零件之间、接口之间、能量流耦合之间的横向关系，在数据、UI、下游分析中全部缺失。

## 四、改造建议（三档，按投入排序）

**A 档｜小改：把已有能力接到生产链路（不动架构）**

1. `_build_user_message()` 真正传入 `parent_context`（父节点/子节点/同级兄弟节点列表）——`function_multi_agent_runner.py:1543`
2. 在 FunctionStepAgent 提示词里加入"关系识别"任务，输出模板 `relations` 不再写 `[]`，并给出同级"功能配合"、接口"接口关联"的判定口径 ——`:1401-1509`
3. `_build_function_network()` 兜底边补齐 `source_function_id` / `target_function_id` ——`:1172-1178`
4. 在 `_assemble()` 里补调 `_build_function_network_detail()`（可直接复用 `step2_function.py:1259` 的实现）——`:1237`
5. 前端给功能表每行加"功能网"入口，挂上已有的 `showFunctionNetwork()` ——`chat.html:7063`

**B 档｜中改：给关系提供数据依据（推荐）**

在结构层引入"接口/接触/相邻"关系（`StructureTreeNode` 增加 `interfaces` 字段，或新建独立的结构关系表），把"这个零件与哪些零件有接口、接口传什么流（电气/机械力/热/流体/信号）"作为输入喂给功能分析 Agent，让零件间关系**由数据推导 + LLM 判断**，而不是纯靠 LLM 猜。这样 A 档第 2 步的准确率会显著提升，也才能稳定产出 `接口关联` / `功能配合`。

**C 档｜大改：打通功能网与失效传导**

启用 `_run_failure_transmission_analysis()`，把功能网的横向关系（同级配合、接口）作为失效传导链的先验，让"零件 A 失效 → 零件 B 失效"的推导有结构依据，而不只是 FE/FC 文本匹配。

---

## 五、一句话给用户/评审的答复

> 功能分析的数据模型从 v4 起就已支持零件间关系（功能配合/接口关联/冗余备份），但当前生产默认走的多 Agent 链路没有启用这套能力：子 Agent 提示词未要求输出关系、输出模板把 relations 写死为空数组、汇总阶段只用结构树父子边兜底，且汇总结果未生成功能级关系明细。因此功能表实际只呈现纵向三级链，零件之间的横向关系（同级耦合、接口、功能流传递）在数据、界面和下游失效分析中均缺失。改造可从"接通已有能力"（A档）起步，若要稳定可靠则需在结构层补充接口关系数据（B档）。
