# 优化措施脚本 vs 需求规格对照梳理

> 对照对象：《AI_DFMEA_需求规格说明书.md》§4.6（阶段6 优化分析）及 §6（AI 自动矫正自查）
> 梳理日期：2026-07-31　｜　范围：仅梳理，未改动任何代码

---

## 一、结论摘要

优化措施的整体框架（生成预防/探测措施、改进后 S/O/D/AP 预估、保存 05-optimization.json、写 DB 基线）**已实现且结构完整**，但存在 **3 个与需求直接冲突/缺失的点 + 2 个半成品字段**：

| 等级 | 问题 | 对应需求 |
|------|------|----------|
| 🔴 冲突 | 触发条件漏掉"违反强制法规的失效项"（无论 AP 等级） | §4.6.2 / V6-1 |
| 🔴 冲突 | 优化 prompt 示例教 LLM 生成"来料检测频次 / 100% 全检"等被明确禁止的措施 | §2.3 / §4.6.3.1 / V6-2 |
| 🟡 半成品 | category（短期/迭代）、cost_impact、maintenance_cost、design_change_type 模型字段齐全，但实际生成链路未打通，落盘数据为空 | §4.6.3.3 / §4.6.3.4 |
| 🟡 半成品 | 改进后 S/O/D 为硬编码规则（S 不变、O-2、D-1），非 LLM 预估 | §4.6.3.2 |
| ⚪ 命名误导 | `scripts/auto_optimize_failure.py` 与"优化措施"无关（是失效分析 prompt 自优化循环） | — |

## 三、需求逐条对照

### 3.1 触发条件（§4.6.2）

> 仅针对：中高 AP 风险项（H/M）+ **违反强制法规的失效项**；不处理低风险且无合规问题的失效项

| 代码位置 | 现状 | 判定 |
|----------|------|------|
| `optimization_tools._is_high_risk` | `rpn >= 80 or ap in ("H","M")` | ❌ 漏法规违规项；RPN 为旧版指标，需求以 AP 为准 |
| `step5_optimization.generate_optimization` | `r.ap in ("H","M")` | ❌ 漏法规违规项 |
| 风险数据侧 | `risk_tools.py` 已正确生成 `regulation_binding` / `regulation_violation` 字段（v12，第 979-980 行），且统计口径 `high_risk = ap=="H" or regulation_violation`（第 1006 行） | ✅ 数据已在，优化侧未消费 |
| 自查校验 `self_check._check_optimization_missing` | 仅查 `ap in ("H") or rpn>=80` | ❌ 与 V6-1 不完全一致 |
| 自查校验 `quality_check` | 仅查 `ap=="H"` | ❌ 同上 |

**实测影响**（项目 15 数据）：467 条风险项中，**41 条 AP=L 但法规违规**（如 GB 4208 密封泄漏、GB 18384 绝缘衰减），按需求仍必须配套优化方案，当前筛选会全部漏掉。

### 3.2 范围限定（§4.6.3.1 + §2.3）

> 仅限设计层面变更（硬件改版/软件逻辑/结构材料/电芯选型/SOR 修正）；禁止产线检验加强、工装夹具、装配工艺、来料管控、售后维保

| 代码位置 | 现状 | 判定 |
|----------|------|------|
| `_OPTIMIZATION_SYSTEM_PROMPT` 示例 | `"增加来料检测频次"`、`"增加100%全检"` 作为正面示例 | ❌ **直接违反需求**（来料管控加严、产线检验加强被明确禁止） |
| `OPTIMIZATION_ANALYSIS_SYSTEM` 示例 | `"增加冗余设计"、"改用高强度材料"、"增加耐久测试"` —— 基本合规，但未写明"禁止制程/售后类"约束 | 🟡 靠 LLM 自觉 |
| 后置过滤 | 无任何剔除制程/装配/来料类措施的校验 | ❌ V6-2 无落地 |

### 3.3 每条方案四要素（§4.6.3.2）

> 同步更新预防措施 + 探测措施 + 预估优化后 S/O/D + 计算更新后 AP

| 要素 | 现状 | 判定 |
|------|------|------|
| 预防措施 | ✅ `preventive_action`（LLM 生成） | ✅ |
| 探测措施 | ✅ `detective_action`（LLM 生成） | ✅ |
| 优化后 S/O/D | ⚠️ 硬编码规则：`improved_s=S 不变`、`improved_o=O-2`（有预防）、`improved_d=D-1`（有探测） | 🟡 属确定性估算，非 LLM 预估；未区分设计变更类型对 S 的影响 |
| 更新后 AP | ✅ `improved_ap = calculate_ap(s,o,d)` | ✅ |

### 3.4 分类 + 成本标注（§4.6.3.3 / §4.6.3.4）

> 短期方案（DV 内）/ 迭代方案（下一代）；每条标注改造成本（高/中/低）+ 长期维护成本

| 层 | 现状 | 判定 |
|----|------|------|
| 数据模型 | `category / cost_impact / maintenance_cost / design_change_type` 字段已定义 | ✅ |
| prompt | `OPTIMIZATION_ANALYSIS_SYSTEM` 有字段说明，但 **tool schema 未声明这些参数** → LLM 无法输出 | ❌ |
| `optimization_tools` 组装 | 输出 dict **完全不含**这 4 个字段 → 05-optimization.json 落盘为空 | ❌ |
| `step5_optimization` 组装 | 取默认值 `"short_term" / "medium"`，永远不变 | ❌ |
| 前端 | `renderOptimization` 表格无 category/成本/设计变更类型列 | ❌ |
| 自查 | `quality_check` 会因 category 缺失扣 15 分（自洽性问题：数据生成时就没写） | ❌ |

### 3.5 输出与自查（§4.6.4 / §4.6.5 / §6.2 SC-6）

| 需求 | 现状 | 判定 |
|------|------|------|
| 输出融合 DFMEA 主表格 | `chat.html` 优化区含：预防/探测/责任人/目标日期/状态/证据/完成日期/改进 S·O·D·AP；`report_tools.py` Excel 导出（19-25 列） | ✅（v4.2 新字段除外） |
| V6-1 高 AP+违规项全配套 | 只查高 AP | ❌ |
| V6-2 仅设计变更 | 无校验 | ❌ |
| V6-3 优化前后变化可验证 | `improved_*` 字段存在 | ✅ |
| V6-4 短期/迭代 + 成本 | 无校验（数据本身未生成） | ❌ |
| SC-6 高 AP 无优化强制提醒 | `self_check` 有 `optimization_missing` 检查器（327-344 行） | 🟡 漏法规违规口径 |
| DB 基线写入 | `upsert_baseline(db_pid, "optimization", data)`（assignee=-1） | ✅ 符合项目 DB 优先约定 |
